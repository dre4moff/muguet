# Performance investigation — fork r4

## Owner's observation and what it implies

On iPhone 17 Pro Max, High textures, reported 30–40 FPS at both 50% and 75% resolution scale. Before the dimension caps/even rounding, 75% renders 2.25 times as many pixels as 50%. Similar FPS is consistent with a CPU/command-processing, frame-pacing or resolution-independent GPU limit. It is not proof of a particular bottleneck. The HUD must confirm that both selected and presented dimensions actually change; a saved explicit `resolution` overrides scale. Compare the same scene, frame-limit setting and thermal state.

The game is WebAssembly compiled ahead of time to ARM64 with Wasmtime/Cranelift's Speed optimization. iOS does not run a Wasm interpreter or JIT. Runtime imports, shared-memory command rings and wgpu's graphics translation still have costs. Lowering pixel count does not eliminate game simulation, visibility/draw-call preparation, vertex work or synchronization. Texture quality mainly changes texture resources; it cannot by itself repair a CPU-bound render path. Do not raise the 5 GiB heap ceiling or the app budget to claim an FPS improvement.

## Source findings and bounded change

Upstream added an extra Binaryen `wasm-opt -O3` preprocessing step in commits [388da687](https://github.com/c22dev/muguet/commit/388da68787cbc83520c13e4946261138d4a18098) and [75d3576b](https://github.com/c22dev/muguet/commit/75d3576bc4e53f514d75f19f2d397c2b7adc9d05), after this fork's base. Earlier personal IPAs did not include that step. r4 incorporates those build/CLI changes, patches hooks/exports before optimization, runs official Binaryen 133 with two worker cores and the upstream feature flags, validates the optimized module and compares its imported/exported function ABI before native precompilation. The owner's ZIP and original Wasm input are unchanged; only the game code embedded in the new personal IPA is regenerated. Binaryen may eliminate/integrate work before Cranelift's native compilation; a smaller module is not an FPS benchmark. Controller-related upstream changes are not applied, following the owner's request to leave their working controller alone.

Upstream [issue 2](https://github.com/c22dev/muguet/issues/2) reports roughly 2,900–3,800 draws/frame, resource growth and CPU-resource termination on another iPhone 17. Those are the reporter's measurements, not this owner's device results or a proven leak diagnosis. A follow-up by the reporter retracts the missing-JS-finalizer hypothesis: the cited userdata hook deletes files, and the browser worker has the same explicit resource lifecycle. The upstream author recommends the increased-memory entitlement. This owner already reports about 6100 MB used; that does not authorize increasing memory policy. No live GPU resource is evicted blindly. r4 preserves the existing live-object report and exposes more timing data.

- The original GPU worker translates commands serially. Ring exhaustion waits on an atomic; engine fence opcode 8 flushes and waits for all current GPU work. At presentation, a triple-buffered uniform slot is not reused until its submission has completed. Those waits preserve correctness; r4 measures them and does not remove them blindly.
- Pipeline compilation has four background workers. While a pipeline is pending, draws are skipped. New scenes can incur shader/variant construction and compilation costs; that does not establish the cause of a persistent 30–40 FPS ceiling. The existing log records pending skips, submits and passes.
- Uniform packing allocated a zeroed temporary buffer for each stage/draw/dispatch, copied constants into it, then copied the entire result into the existing staging ring. r4 writes directly into the staging ring. Padding and absent/short constants are still zeroed on reuse. Shader layout, bind-group identity, dynamic offsets, GPU upload, synchronization and game inputs are unchanged. This removes a proven allocation/copy cost; its contribution to total frame time on iPhone remains unmeasured. A release-mode Mac microbenchmark (five runs of 100,000 blocks) reduced this isolated packing/copy cost by about 41–49% at 1/4/16 KiB. It does not imply a 41–49% FPS improvement.
- The launcher defaults to a 60 FPS engine cap (`-frameLimit=1`) and Fifo presentation where Mailbox is unavailable. Extra arguments may override the cap. 30–40 FPS alone does not prove an intentional 30 FPS cap, and the event loop's controller polling is separate from the engine/render workers. No frame pacing or controller behavior is changed.
- Source reports a 5 GiB enforced shared-memory maximum but upstream's `emscripten_get_heap_max` shim advertises 16 GiB. This is a contract inconsistency, not evidence of this owner's FPS limit; no heap-policy change is included in r4.

## Diagnostic HUD

Enable Performance HUD for investigation. In addition to FPS/dimensions/memory/thermal state, r4 shows:

| Field | Meaning and limits |
| --- | --- |
| Renderer CPU ms/f | Actual CPU time of the native graphics worker, divided by visible frames. Includes driver/command translation and profiler work on this thread; not CPU time of the game's render thread. |
| App CPU cores | Whole-process CPU seconds per wall second; 1.0 means the equivalent of one continuously busy core. Not percentage utilization of the whole phone and not proof of single-thread saturation. |
| Cmd idle | Graphics worker's atomic-ring waiting time per visible frame. Can indicate engine preparation, game pacing, I/O or another wait upstream. |
| Fence | Existing engine GPU fences plus uniform-slot reuse waiting, per visible frame. Backpressure is not the same as GPU execution time. |
| Drawable | Surface acquisition wall time. Helps distinguish presentation waits. |
| Submit / uniforms | CPU-side submission wall cost and packing wall cost; not GPU duration. MiB/f counts logical uniform bytes. |
| Readback / fences / new groups | Operations during the current HUD window, not frame averages. |
| I/O ms/f | Aggregate native file-read service wall time per visible frame on its own worker. Overlaps other work; exclude it from an additive frame-time budget. |
| GPU pass sum / span | Asynchronous boundary timestamps for draw and compute pass sites (including proxy/mipmap/presentation draws), sampled every 16 engine frames. Sum adds pass intervals (overlap is possible); span includes gaps between first/last pass, including submission/CPU gaps. Neither is a direct GPU utilization measurement. Transfer-only work and standalone clear/resolve-only passes are not separately timed: Apple boundary counters can leave the fragment-end timestamp zero for such passes. Synthetic drawn passes also showed an occasional missing endpoint; this is handled as partial coverage, not zero GPU cost. |
| Samples / age / errors | Rolling maximum of eight completed sampled frames, age of newest completion, and timing failures. Capacity exhaustion or missing/zero/reversed timestamp pairs is reported as partial. Do not infer a full GPU frame budget from partial samples. Frames with no valid pair increment timing errors and produce no fabricated duration. Unsupported adapters show unsupported instead of invented GPU values. |

GPU profiling uses three bounded slots, each with 2048 timestamps and two 16 KiB buffers: 96 KiB of explicit buffers plus driver query storage. Slots are reused only after successful map completion and unmapping; failed slots are disabled instead of reused. A busy pool skips sampling instead of waiting. Resolve/copy is appended to the normal final submission; timestamp readback adds no synchronous wait. Boundary descriptor timestamps support Apple GPUs; arbitrary encoder/inside-pass timestamps are not requested. Timestamps are explicitly normalized to nanoseconds through wgpu. With HUD off, no timestamp feature, query set or sampling buffers are requested and no CPU/I/O clocks are sampled on hot paths. Measurement has overhead; compare final gameplay FPS with HUD off as well.

Interpret several steady windows after compilation settles. High renderer CPU time implicates command translation. High command idle with little renderer CPU suggests a limit upstream, but cannot distinguish game simulation from pacing by itself. High fence/drawable times implicate backpressure/presentation. GPU pass times that grow with resolution help identify shading cost. Low headroom and Hot/Critical thermal state require separate consideration. Do not add overlapping counters to reconstruct one frame or extrapolate from a Mac correctness test.

## Why the old MetalFX path regressed, and Madeira comparison

Apple's performance mechanism is rendering fewer pixels, then reconstructing a fixed larger output. r2 held the selected game input fixed and multiplied reconstruction output by 1.5/2 (2.25/4 times the output pixels). It added GPU image-motion search, full-frame conversions, history copies and cross-queue synchronization without reducing game rendering relative to Off at the same selected scale. It also lacked coherent engine geometry motion/jitter information. More GPU work and unreliable reconstruction explain why the integration could regress; exact iPhone cost was not recorded.

The current Madeira release v0.1.3-fork-r38 was checked against GitHub source blobs. Its Off/1.5/2 display option uses the MetalFX **spatial** scaler in the native command stream, with a selected-output ceiling and bypass when input already reaches that output. Its temporal path is a separate NGX/DLSS bridge using game-provided motion/depth/jitter, and must not be confused with that selector.

Muguet uses wgpu 30's deferred encoding path. Its raw HAL API explicitly panics if mixed with wgpu recording on the same encoder (`vendor/wgpu-core/src/as_hal.rs`, `command/mod.rs`). Native MetalFX cannot simply be inserted into the current encoder like DXMT's native scaler; a compatible command-stream extension/backend integration and lifetime/tracking validation would be needed. A separate raw submission could be designed, but would not demonstrate the same integration/cost behavior. r4 therefore keeps MetalFX completely absent, following the owner's instruction to include it only with the Madeira-style integration. This is a limitation of the current integration, not a claim that MetalFX is impossible for Muguet in future.

Primary references: [Apple's MetalFX rendering and input requirements](https://developer.apple.com/videos/play/wwdc2022/10103/), [wgpu timestamp feature support](https://docs.rs/wgpu/30.0.1/wgpu/struct.Features.html), [Madeira r38 native presentation source](https://github.com/dre4moff/dxmt/blob/67d27a82c4ab016394eea0fd45c267ab39562a64/src/d3d11/d3d11_swapchain.cpp).

## Acceptance boundary

Host byte-equivalence tests, synthetic microbenchmarks, Metal timestamp correctness, compilation and unsigned-package verification do not establish iPhone gameplay or an FPS gain. A fresh same-scene 50%/75% comparison on the owner's iPhone, with both dimensions visible and the new timing fields, is required to identify the dominant path. Game-data ZIP, original Wasm input, controller behavior, memory limits, import cleanup, licenses and unsigned installation workflow are preserved. Optimized embedded game code is newly generated using the upstream preprocessing step.
